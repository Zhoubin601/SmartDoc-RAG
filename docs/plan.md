# SmartDoc-RAG 高分优化执行计划

> 目标：在不盲目扩大技术栈的前提下，把项目打磨成一个**核心流程可运行、LangChain 使用讲得清楚、测试结果可复现、开源文档与源码一致**的智能应用。
>
> 课程截图的明确要求是基于 LangChain 和在线或离线大模型开发智能应用，并提交 README 与公开 GitHub 仓库；截图没有强制要求 Vue、Spring Boot、Docker 或公网部署。因此，优先保证功能质量与技术说明，不为堆技术而增加无必要的复杂度。
>
> 任务状态规则：只有在当前代码版本中实际完成并验证后才勾选 `[x]`。历史过程文档里的测试记录不自动等于当前版本已验收。

## 阶段三：P0——优先修复核心正确性（最高优先级）

### P0.1 修复向量库保存与恢复

- [ ] 保存并恢复 TF-IDF 向量器状态（包括词表、IDF 等），不能只保存文档和向量矩阵。
- [ ] 恢复时校验文档数量、向量行数和特征维度；不一致时给出明确错误，禁止静默继续。
- [ ] 在应用启动流程中提供恢复已有知识库的能力；如果暂时不做自动恢复，则明确说明重启后需重新构建，并避免宣称支持持久化恢复。
- [ ] 增加回归测试：构建索引 -> 保存 -> 销毁旧对象 -> 加载 -> 使用相同问题检索，比较恢复前后的命中文档与排序。

**验收标准：** 恢复后的查询向量与已保存矩阵处于同一特征空间；查询不会因为维度不一致而失败；相同查询的结果可解释且稳定。

### P0.2 让“多轮对话”描述与实际行为一致

- [ ] 选择并落实一种方案：
  - 推荐：在 RAG 提示词中注入有限轮数的历史对话，并明确历史消息只用于理解当前问题，事实依据仍来自检索到的文档；
  - 或者：暂不支持上下文记忆，并同步修正 README 与界面文案。
- [ ] 增加连续追问测试，例如先询问文档中的某项配置，再问“它的默认值是什么”，检查系统是否正确理解指代。
- [ ] 避免把仅在界面显示历史消息描述成模型具有记忆能力。

**验收标准：** 连续追问有可重复的测试结果；系统不会将先前模型回答当成比原始文档更可靠的事实来源。

### P0.3 提升检索相关性与无答案处理

- [ ] 准备一组固定的中文测试问题，覆盖文档明确可回答、同义改写、关键词较少、文档未提及、与文档完全无关等场景。
- [ ] 记录每个问题的预期来源片段和实际 Top-K 检索结果。
- [ ] 基于测试评估是否需要最低相关性阈值；阈值应通过样例确定，不能凭直觉随意设置。
- [ ] 当检索不到可用资料时，向模型传递明确的无相关资料状态，提示其说明资料不足。
- [ ] 在界面中区分“检索相似度分数”和“答案置信度”；不得把相似度分数直接当成回答正确概率。

**验收标准：** 文档内问题能够召回相关片段；文档外问题在测试集上能合理拒答；对阈值选择及其局限有简短说明。

### P0.4 完善文档解析与 API 异常反馈

- [ ] 对空文件、解析后无文本的 PDF、损坏文件、暂不支持的扩展名给出明确反馈。
- [ ] 解析多个文件时分别显示成功与失败清单，避免一个文件失败导致用户无法判断整体处理结果。
- [ ] 捕获模型调用的网络错误、鉴权失败、限流和超时，并在 UI 提供可理解的提示；详细异常可记录到日志，不向用户泄露 API Key。
- [ ] 检查 Embedding 调用失败时的降级逻辑：不能只在创建模型对象时捕获异常，还要考虑实际生成向量时的网络或鉴权失败；降级必须保持文档向量和查询向量使用同一套模型/特征空间。

**验收标准：** 常见异常能给出清晰提示；应用不会静默切换到不兼容的向量表示，也不会将凭据写入日志。

### P0.5 校准源码、README 与功能承诺

- [ ] 检查根目录 `README.md`、`Code/README.md`、`output/` 课程说明文档和实际源码是否一致。
- [ ] 当前问答链若未使用 `RunnablePassthrough`，就修正文档描述，或在确实需要时再补充实现。
- [ ] 如默认方案使用 TF-IDF 字符 n-gram，明确说明它是轻量文本相似度检索，不把它称为深度语义 Embedding。
- [ ] 删除或改写“杜绝幻觉”“高精度语义检索”“企业级”等无法由测试直接支撑的绝对化承诺。
- [ ] 只列出当前版本已实现并验证的功能；离线大模型、自动恢复、多轮记忆等未验证能力不得提前写成已完成。

**验收标准：** 老师按 README 阅读代码时，架构图、组件名称、默认模型路径、检索方式和功能边界均能对应到真实实现。

## 阶段四：P1——建立可复现的测试证据（核心冲分项）

### P1.1 建立自动化测试目录

- [ ] 新增 `Code/tests/`，按模块组织测试。
- [ ] 覆盖文档解析与切分、向量检索排序、空输入、持久化恢复、无相关资料、模型异常处理。
- [ ] 对大模型调用使用 Mock/Fake 模型完成稳定的单元测试，避免单元测试依赖网络或消耗 API 额度。

**验收标准：** 其他人安装依赖后可以用一条命令运行测试；测试有明确断言，而不是仅仅打印日志或手动观察输出。

### P1.2 做一份小而可信的 RAG 评测集

- [ ] 准备一份不含隐私的演示文档，并编写至少 8—12 个测试问题。
- [ ] 每个问题记录：问题类型、预期答案要点、预期来源、实际检索片段、实际回答、是否通过。
- [ ] 至少包含：文档内直接问题、同义改写问题、跨段落问题、文档外问题、模糊问题。
- [ ] 统计基本结果，例如预期来源是否进入 Top-K、文档外问题是否合理拒答；如报告百分比，必须注明测试集规模与计算方式。
- [ ] 不编造测试结果，不用少量样例声称达到普遍准确率。

**验收标准：** 仓库中有可复现的测试样例和结果记录，能够解释项目目前的能力边界。

### P1.3 完成干净环境端到端验证

- [ ] 单独验证无效 API Key、网络/API 失败、空文档和文档外问题。
- [ ] 记录运行环境、执行命令、真实结果和已知限制；测试截图中隐藏 API Key 与个人隐私。
- [ ] 只把当前版本真实跑通的场景标记为通过。

**验收标准：** 不依赖开发者机器上未记录的环境状态；新用户能按说明复现主流程。

## 推荐执行顺序

1. P0.1 向量恢复正确性。
2. P0.3 检索相关性与无答案处理。
3. P0.4 异常反馈与降级安全。
4. P0.2 多轮对话行为（实现或准确说明）。
5. P1.1 自动化测试与 P1.2 评测集。

> 冲分原则：优先做“可以演示、可以测试、可以解释、可以复现”的功能；不追求功能清单越长越好。
